**2026-11-15 — Final verification pass after the C7/C8 replacement: fixes and findings**

Verification only; nothing in C7/C8, the backend, the rule engine or the thresholds was redesigned.

- **Build:** `@axe-core/playwright` added to `devDependencies` (the C16 axe test imported it but it was never declared, so `next build` failed its type check). The stale `@ts-expect-error` in `tests/ci/noFakeData.test.ts` was removed: with `allowJs` the `.mjs` import is type-checked, so the directive itself was the error; no assertion changed.
- **`dark:` utilities now follow the app theme, not the OS** (`@custom-variant dark` in `globals.css`). The app is dark unless `data-theme="light"` (SPEC §8.4), but `dark:` was tied to `prefers-color-scheme`, so on a light-mode OS the dark background got light-theme text colours. axe found contrast failures on nearly every screen in that case (and the bottom bar rendered white). One rule; no component changed for this.
- **Ten grey text classes raised to pass WCAG AA** (`text-zinc-500` on the dark background is 4.1:1; now `text-zinc-600 dark:text-zinc-400`): `OfflineBadge`, `CrewCard`, `CrewScreen` (2), `CheckinWizard`, `MeasurementCard` (2), `MeasurementsStep`, `MoodStep`, `NumberStepperInput`. Colour only.
- **Offline navigation on a fresh install was broken (rule 1).** The service worker precached only the start page and static files; other routes were stored only once their links had been on screen while online, kept for 24 hours and at most 32 entries (plugin defaults), under a URL whose query changes with the current screen. A device that went offline before the first unlock could not open Check-in, Body or anything else, and the project's own offline test failed. Fix: `lib/pwa/useOfflineRouteWarmup.ts` (called from the app layout) prefetches every route in `lib/pwa/appRoutes.ts` once the worker controls the page, and a runtime-caching rule in `next.config.ts` (`ahm-route-prefetch`) keeps those payloads with no expiry and ignores the query string on lookup. `tests/pwa/appRoutes.test.ts` fails if a new page is not listed.
- **Not fixed, by choice:** reloading the browser while offline on a screen other than Home still depends on that page having been loaded as a document before (the start page is always available). In normal use the app is opened at Home.
- **`tests/e2e/helpers.ts` `completeCheckin`** waited for the text "Rule ", which a green result never shows (it shows "Rules version N"), so the offline test could not pass with its own heart rate of 72. It now waits for "Rules version N". Same strictness: it still proves the result screen was reached.
- **Model licence (open, not changed):** `body.glb` is built from BodyParts3D release 3.0 as published by a mirror under CC BY-SA 2.1 Japan. SPEC §8.3 asks for "CC0 or CC-BY". The official archive (dbarchive.biosciencedbc.jp, licence page updated 2025-02-27) now states CC BY 4.0 and offers release 4.0; whether that statement also covers the old 3.0 files is not written anywhere on it. Options are in the hand-off note; the model was not replaced and the README still states CC BY-SA 2.1 Japan.

**2026-11-15 — C7/C8 replaced: anatomical 3D body with selectable organs**

Requested as a replacement of C7 and C8 only. Nothing outside the body screen, its config, its store and its styles was changed; no backend, schema, rule or threshold change.

- **Model: BodyParts3D release 3.0, CC BY-SA 2.1 Japan** (© The Database Center for Life Science). Chosen because it is the one openly licensed source found with every organ as its own mesh. **This supersedes the earlier "CC0 or CC-BY only" note and the "user downloads the model" note** — the request asked for a model to be found and bundled. Share-alike applies to `body.glb` (a derivative, offered under the same licence), not to the app's code. Credit and modifications are in README. **Open item for the user:** confirm CC BY-SA is acceptable for the submission; if not, any other GLB with the same mesh names drops in.
- **`body.glb` is generated, not hand-made:** `frontend/scripts/body-model/build.mjs` (own `package.json`, not an app dependency) downloads the listed FMA concepts, merges, simplifies, Draco-compresses. 17 meshes (skin + 16 organs), about 130,000 triangles, 665 KB. Re-run it to change detail levels or add an organ.
- **Organs vs regions.** A region (SPEC §8.3 table) is what has text and data. An organ is one mesh. Each organ is hoverable/clickable on its own and opens its region's panel, titled with the organ's name. `BodyPart.meshName` became `BodyPart.organs[]`. Mapping: brain → Head / Brain; eyes → Eyes; heart → Heart; left lung, right lung, windpipe → Lungs; spleen, thymus → Immune system; stomach, liver, pancreas, small and large intestine → Gut; spine → Bones / Spine; left and right kidney → Kidneys. Mind, Muscles and Skin have no organ mesh and keep a marker (`RegionHotspot`).
- **No liver/stomach/spleen region of their own.** The SPEC has no indicator, threshold or text for them, and CLAUDE.md rule 6 forbids writing medical content. They are real, selectable organs that show their region's real data; a missing reading says "No data yet".
- **Status colours stay the app's status tokens** (green/yellow/red/critical, grey for no data). The request suggested cyan for "normal"; cyan is used instead for hover, selection and scene chrome, so a body colour always means the same as the badge next to it. Only `critical` pulses, as everywhere else.
- **Data path unchanged:** the screen reads the astronaut's saved evaluation, logs and symptoms through the existing `lib/db/repo` functions (IndexedDB, kept in step with the server by the existing sync). No new endpoint, no direct API call from the screen (offline-first rule 1). New in the panel: rule id per indicator, check-in date, and a sparkline of the last 7 saved values.
- **"What to do now" needs a finding in that region.** The engine tags actions by category, not region, so the old panel could show heart-rate advice under Kidneys with no kidney data. Actions now appear only if the region has a status from a real reading or a recently reported symptom. No action text was changed.
- **One selection, one panel.** `useBodySelectionStore` holds `selectedRegionId` + `selectedOrganId`; the panel is keyed by region inside `AnimatePresence mode="wait"`, so a new pick closes the old panel first. The canvas is never remounted on a switch.
- **The body screen is always dark** (`.holo-root`), in either theme. `dark:` utilities are forced on inside it through one `@custom-variant` in `globals.css`; outside it they behave as before.
- **Layout follows the container width** (ResizeObserver, 960 px), not the window, so the crew drill-down gets the stacked layout when it is narrow. Wide: region list left, panel right, camera view shifted so the organ is not under the panel.
- **Reduced motion:** no auto-rotation, no scan sweep, no ring spin, no pulse; camera and panel changes are instant. The scene then renders only on change (`frameloop="demand"`).
- **Empty-state sentence kept word for word** ("No data yet. Complete a check-in to see this region's status.") because C16's e2e test looks for it. With no check-in the panel still opens (function text, hazards, sources) with every reading shown as "No data yet".

**2026-11-15 — C15 crew overview choices**

- **The overview lives at `/crew`, reached from More, and the link is shown only to commander, surgeon and admin.** Access is checked three times: the More row is hidden, the page refuses to render for the astronaut role, and every function in `lib/db/crewRepo.ts` takes the viewer's id and re-checks the role (`CrewAccessError`). `admin` is included because it already has crew-wide read on the server (`CREW_READ_ROLES`).
- **On one device the overview reads the local registry (Dexie), not the API.** SPEC screen 10: "on a single device it reads the local registry"; other devices' astronauts appear after a sync. No `/ground/*` endpoints were added: sync already carries everything the overview needs, and an online-only screen would break rule 1.
- **Read-only drill-down = the normal `HomeDashboard`, `TrendsView` and `BodyView` with `astronautId` + `readOnly`.** In read-only mode the dashboard drops the check-in button, action checkboxes, reminder prompts, rewards and the environment link; trends and body have no data controls to begin with (rotate/zoom/select change the view only). The 30-day charts are the Trends tab's 30-day range.
- **Sparklines on the overview: heart rate, sleep hours, mood** (last 7 logged days, real values only; fewer than 2 values shows text instead of a line). Three is what fits a phone-width card; the full set is one tap away in the drill-down.
- **Flags = non-green rule results of the latest stored evaluation plus a live `TRD-MISS-01`** computed for today (the "alert on surgeon view" half of that rule), so an astronaut who stopped checking in rises in the worst-first sort even though their last stored result was green. No new rules or thresholds.
- **Surgeon notes: only the surgeon role writes; commander and admin read; the astronaut does not see them in this build.** Notes are append-only (no edit, no delete, 1000 characters), stored with author name and crew ID, and synced (`surgeon_note`; the server rejects non-surgeon authors and deletes). Whether the astronaut should see notes about themself is an **open item to confirm**.
- **Audit log: one local entry each time a commander/surgeon/admin opens another astronaut's drill-down** (who, role, whom, when), shown under the overview and pushed to the server's `audit_log` (`audit_entry`, push-only, de-duplicated by client id, cannot be deleted). Opening your own row is not logged. Listing the overview itself is not logged, only opening a person.
- **Limit (SPEC §13, unchanged):** this is a role check inside the app, not encryption. Anyone with the device and browser dev tools can read IndexedDB; PIN-derived encryption of local data remains the "later enhancement" the spec names.

**2026-11-14 — C14 sync implementation choices**

- **Sync is device-to-server, protected by one shared key, not per-astronaut tokens.** A shared tablet holds several astronauts' records and must send all of them whoever is unlocked, and a new device must be able to load the crew before anyone can unlock. So `/sync/push` and `/sync/pull` require an `X-Sync-Key` header equal to the server's `SYNC_KEY`; with no key set the endpoints answer 503 (sync off). **Consequence to confirm:** anyone holding the key can read and write every astronaut's records, and it is stored in plain form in the device's IndexedDB. This matches SPEC §5.1's "PIN is a convenience lock, not strong security" but is weaker than the per-astronaut rules on the other endpoints. PIN/security level is already an open item in CLAUDE.md §8.
- **The PIN hash and salt are synced** (`astronauts.client_pin_hash/salt`), which is what lets a second device unlock the same astronaut with the same PIN. A 4 to 6 digit PIN hash is weak if intercepted; on a LAN without TLS it travels in the clear. The server can also verify a PIN against this app-format hash, so an astronaut registered on a device can sign in to the API (needed for the commander/surgeon views in C15).
- **Records travel and are stored verbatim.** Each synced table has a `payload` column holding the app's record exactly as sent; `/sync/pull` returns it unchanged, so app-only fields (`selfHarmThoughts`, `firstReadings`, reminder `kind`/`weekday`) round-trip with no mapping. Typed columns are filled alongside for server-side queries. This closes the C12/C13 open item about those fields. Rows created through the typed C12 endpoints have no payload and are **not** delivered by pull.
- **The pull cursor is the server's clock** (`server_updated_at`, set by the server on every change), never a device's `updatedAt` (SPEC §17 item 8). `serverTime` is read before the queries, so a pull can re-deliver a change but never skip one.
- **Exactly once:** an outbox row is deleted only after the server has answered for it. If the answer is lost the row is sent again; the server recognises an identical record and reports it accepted without storing it twice.
- **Version conflict (one record changed on two devices):** the copy with the newer `updatedAt` becomes live; a tie goes to the server. The other copy is kept verbatim: in `sync_conflicts` on the server, and in the new Dexie `conflicts` store on the device whose copy lost. When a device's copy wins, the server bumps the version above both so every device takes it.
- **Same-date conflict (two different check-ins for one astronaut and date):** the one already on the server stays live, whichever is newer; the incoming one, with its symptoms and result, is kept in the archives on both sides. First-to-server-wins was chosen over newer-wins here because replacing a log and everything under it across devices would need tombstones for a rare case. **Open item to confirm.**
- **Nothing in sync deletes a health record.** Deletes are soft on the server (`deleted_at`, payload kept). Conflict copies are never removed, are listed on the Sync screen ("Kept copies"), and are included in exports.
- **Records the server refuses** (impossible values, unknown astronaut, a crew ID already used by a different identity) leave the outbox, stay on the device, and are listed on the Sync screen with the reason. Two devices that each registered the same crew ID offline are **not** merged.
- **Each record is sent once per batch, as its latest state** (several outbox rows for one record collapse to the last). Batches of 50, oldest first.
- **Backoff:** 2 s, 4 s, 8 s ... capped at 5 minutes, no random jitter (deterministic; also keeps `Math.random` out of app code for C16). Coming back online resets it. A wrong key or sync switched off is not retried on a timer.
- **Reachability is `GET /health` with a 2.5 s timeout**, tried only if `navigator.onLine` is true (SPEC Appendix D).
- **Service worker: backend calls are never cached** (a `NetworkOnly` rule for `/api/v1/`). The plugin's default cross-origin rule would have answered `/health` from cache while offline, making an unreachable server look reachable.
- **`reloadOnOnline` turned off.** The PWA plugin reloaded the page whenever the browser came back online, which locked the app and would discard a half-filled check-in. Found by the end-to-end test.
- **Sync setup is also on the Crew screen** ("Load crew from a server"), because a new device has no astronaut to unlock and so could not otherwise reach the Sync screen.
- **Sync runs while the app is locked**, like the reminder scheduler.
- **Export/import:** JSON and CSV export work offline; an astronaut exports only their own data, a commander/surgeon/admin everything on the device; PIN hashes are never exported; CSV cells that start with `=`, `+`, `-` or `@` are neutralised. **Import is JSON only** (the app's own export format); CSV is one-way. Import only adds records for astronauts already on the device, never overwrites a newer local record, and queues what it adds for sync.
- **Dexie schema is now version 2** (adds the `conflicts` store). **Backend migration `0002`** adds the sync columns and `sync_conflicts`; it was tested on a database that already had rows.
- **Not built:** `sync_service` clock-skew correction beyond the server-time cursor; surgeon-originated reminders; and nothing pushes a gamification snapshot (the server's `/gamification` stays empty).
- **Observed, pre-existing (C4), not changed:** "Update today" starts the check-in from blank and replaces the day's values, so re-saving with only heart rate filled drops that day's other measurements. Seen in the two-device test; sync carried the result faithfully.
- **Verified end to end** with a real backend on SQLite and two separate browser profiles: registered and synced on device 1; went offline, saved a check-in (server unchanged, 2 changes waiting); reconnected and it synced by itself in under a second; three more "Sync now" presses changed nothing on the server (1 astronaut, 1 log, 1 result); a fresh device 2 connected from the Crew screen, showed the astronaut, unlocked with the same PIN and showed the same values; an edit on device 2 reached device 1. Not tested against PostgreSQL.

- **Result: the two engines agree.** The Python engine passes all 99 vectors in `shared/rule-test-vectors.json` unchanged, and its complete output (messages, action order, escalation text, explanation lines) is identical to the TypeScript engine's for every vector. No vector or threshold was changed to get there.
- **`thresholds.json` is generated, not hand-written.** `frontend/tests/rules/serverParity.test.ts` writes `backend/app/services/rule_engine/thresholds.json` from `config/thresholds.ts` (plus the adaptation constants from `config/environments.ts`) when run with `AHM_WRITE_PARITY=1`, and on every normal test run fails if the file no longer matches. `config/thresholds.ts` stays the one place a value is edited.
- **`shared/rule-engine-golden.json` added** (same generator, same staleness check): the TypeScript engine's full output per vector. The Python tests require an exact match. This is stricter than the vectors, which list only statuses and rule ids. It is test data under `shared/`, never imported by app code.
- **The Python engine works on plain dicts with the TypeScript key names** (`ruleId`, `windowDays`, `rulesVersion`, `selfHarmThoughts`, `missionDay`), so inputs and outputs are interchangeable between the two engines without a mapping layer.
- **Numbers in messages are printed as JavaScript prints them** (`72.0` -> `72`) so message text is identical.
- **`symptoms.py` holds only shared symptom lookups**: as in the TypeScript engine, SPEC §4.4 defines no single-symptom rule independent of a combination, so there is no separate symptom-rules stage.
- **`POST /evaluate` is stateless by default** (SPEC §7.3): the result comes from the request body alone and nothing is saved. If the body names `log_id` of one of the caller's own stored logs, the result is stored in `evaluations` with `rules_version`; sending the same `evaluation_id` again replaces the row. Storing on another astronaut's log is refused for every role. It needs a token, like every health-data endpoint.
- **`/evaluate` rejects unknown keys** (a misspelt field would otherwise be silently left out of the evaluation) and applies the same sanity ranges as a stored log. All 99 vectors pass through the HTTP layer with unchanged results.
- **`GET /evaluations/latest` added** (SPEC §7.3), with the usual read rules; the crew list's `latest_overall_status` is now real.
- **Still open from C12:** `selfHarmThoughts` reaches the engine through the `/evaluate` body but has no column on `daily_logs`.

**2026-11-14 — C12 backend core implementation choices**

- **Everyone may write their own data; nobody may write another astronaut's.** SPEC §7.3 says commander/surgeon tokens "write nothing". Read literally, a commander (who is also a crew member with their own check-ins) could never sync their own logs. Implemented: reads of another astronaut's data need commander/surgeon/admin; writes to health data are own-only for every role; so commander and surgeon are read-only for everyone else's data. **Open item to confirm.** Surgeon notes (the one cross-astronaut write in the SPEC) are C15.
- **Registration: first-run, then admin only.** With zero astronauts in the database, `POST /astronauts` needs no token (there is nobody to sign in as) and may create any role. After that only an `admin` can register astronauts. An astronaut can update their own profile, environment, mission dates and PIN; only an admin can change a role or crew ID or edit someone else. Commander and surgeon cannot edit other profiles.
- **Role and active state are read from the database on every request**, not trusted from the token, so demoting or deactivating someone takes effect immediately.
- **PIN hashing: PBKDF2-HMAC-SHA256, 310,000 rounds, random salt, standard library only.** The server hash is independent of the client's own PBKDF2 hash; how PINs travel in sync is C14's question. **No login rate limiting**: a 4-digit PIN can be guessed by brute force over the LAN. Known limitation; PIN/security level is already an open item in CLAUDE.md §8.
- **`SECRET_KEY` defaults to `change-me`.** Tokens are forgeable until it is changed. Documented in `.env.example`; not enforced.
- **JWT via PyJWT (HS256)**; token lifetime `ACCESS_TOKEN_MINUTES`.
- **Schema differences from the SPEC §6.2 listing:** `astronauts.gravity_changed_on` added (C10); `advice_followups` stores `response` (`yes`/`partly`/`no`) and `followup_date` instead of a `followed` boolean, because that is what the app records; `advice_followups.evaluation_id` has no foreign key (the client creates evaluation ids before any evaluation is stored server-side); `reminders.local_time` is `HH:MM` text and `reminders.deleted_at` exists for soft delete; NUMERIC columns are `Float`; arrays are JSON. The client-only log fields `selfHarmThoughts` and `firstReadings` have no column yet — C13/C14 must decide.
- **Reminder shape is the SPEC's** (`kind`, `local_time`, `days_of_week` 1=Mon..7=Sun, `message`), not the client's (`label`, `time`, optional `weekday` 0=Sun). C14 maps between them.
- **`/gamification` stores a snapshot.** The app derives points from its own data (C11), so the server has `GET` and `PUT /gamification` for a snapshot the client sends; with nothing stored `GET` returns zeros and `updated_at: null`. The server does not recompute points.
- **`POST /symptoms` treats the sent list as the whole truth for that log**: entries not in the list are soft-deleted, so an empty list means "None today". `GET /symptoms` and `GET /followups` were added (not in the SPEC table) so the read rules can be exercised.
- **`GET /logs/today` takes an optional `on=YYYY-MM-DD`**, because "today" is the mission-local date, which the server cannot know; it defaults to the server's date.
- **One log per astronaut per date:** a second log id for the same date is a 409, not a silent overwrite. C14's conflict handling builds on this.
- **Audit log:** every read of another astronaut's data by commander/surgeon/admin writes a row (`actor`, `read`, entity, astronaut id). Reads of one's own data are not logged.
- **CORS:** the exact origins in `CORS_ORIGINS` (default now `http://localhost:3100`, the frontend's port) plus, by default, any origin on localhost or a private LAN range, any port (`CORS_ORIGIN_REGEX`). CORS is browser policy, not access control: every data endpoint still needs a token.
- **Not built in C12 (owned by later chunks):** `/evaluate` and `/evaluations/latest` (C13), `/sync/*` (C14), `/ground/*` and surgeon notes (C15). The `evaluations`, `sync_devices` and `audit_log` tables exist now so the first migration is complete.
- **Migrations:** one reviewed initial revision (`0001`), schema only. Verified by running upgrade and downgrade on SQLite, and by compiling the same migration to PostgreSQL SQL (`alembic upgrade head --sql`: native `UUID`, `JSON`, `TIMESTAMP WITH TIME ZONE`, `BIGSERIAL`). **Not run against a live PostgreSQL/Neon database** — none is available on this machine and C: has no room for a Docker image.
- **The API never creates tables or rows at startup**; `alembic upgrade head` must be run once before first start.
- **Tests write their temp SQLite files to `backend/.pytest_tmp`** (pytest `--basetemp`), not `%TEMP%` on C:.

**2026-11-14 — C11 gamification implementation choices**

- **Nothing is stored; everything is derived.** Points, level, streak, badges and the weekly challenge are recomputed from the astronaut's own saved check-ins and action records each time (`lib/gamification/engine.ts`, pure; `lib/db/gameRepo.ts`, read-only). There is no gamification row to write, sync or drift, so the Dexie `gamification` table stays empty and no outbox rows are produced. Consequence for C12/C14: the server `gamification` endpoints in SPEC §7.3 have nothing to receive from this client; the same numbers can be derived server-side from synced logs.
- **Guardrails are structural.** The engine's input type has no symptoms and no status, so neither reporting a symptom nor a red/critical day can change any number (tested end to end: chest pain + critical earns exactly what "None today" + green earns). A measurement earns points for being logged, never for its value. Day-count badges and the weekly challenge count days that reach a fixed mark; exceeding it earns nothing more.
- **"Each measurement +5 (max 40)" counts measurement cards**, so blood pressure (two numbers) and exercise (two numbers) each count once. Ten cards exist, capped at 40 points a day. Mood and stress are not measurements for points.
- **"Action completed +10" vs "follow-up answered +5".** Both live in the `followups` table (C5 decision). A row whose evaluation is from the same date is an action ticked on Home (+10, removed again if unticked); a row whose evaluation is from an earlier day is a yesterday-recap answer (+5 for Yes, Partly or No alike, so there is no reason to answer anything but the truth).
- **Freeze token is applied automatically**: a single missed day does not break the streak if no freeze was used in the previous 14 days. The frozen day is not counted as a streak day. Two missed days in a row end the run. With today still open, a streak that ended yesterday is still active; one that ended the day before shows as "frozen" if a freeze is free.
- **Late (backdated) check-ins count as check-in days**, since they are real saved check-ins. A late entry can therefore repair a streak; accepted, because SPEC allows late entry for the last 14 days.
- **"7-day streak bonus +50" is paid for every full 7 days in a run** (14-day run = 100).
- **Day-count badges are cumulative, not consecutive** ("7 nights >= 7 h" = any 7 logged nights). Simplest reading; Mission Marathon is the only streak badge. Hydration Hero's "target" is the bottom of the green band of `water_ml` in `config/thresholds.ts`, not a second number.
- **Full Spectrum** needs heart rate, blood pressure, glucose, temperature, SpO2, sleep, exercise and mood in one day. The symptoms checklist (also in SPEC's MVP list) is part of every check-in and is deliberately not a condition.
- **Open item to confirm: Calm Mind ("7 days mood >= 4") rewards reporting a good mood**, which sits uneasily with the "no incentive to hide how you feel" guardrail. It is in SPEC §11, so it is implemented as written, but it is the one badge that depends on a self-rating.
- **One fixed weekly challenge** (SPEC's own example, "5 nights of 7+ hours"), Monday to Sunday, shown as a ring on Home and on Rewards. No rotation.
- **No shaming**: the Rewards screen never mentions a health status as good or bad, never shows a lost-points or failed state, and a broken streak reads "A new streak starts with your next check-in."
- **Not built:** a "+N points" line on the check-in result screen, and any crew leaderboard (SPEC: "not competition").

**2026-11-14 — C10 Learn pages and environments implementation choices**

- **Learn `.md` files hold prose only** (What it is / Why it matters in space / When to worry). How-to-measure steps, ranges and per-status tips on each Learn page are rendered from `config/thresholds.ts`, so a Learn page cannot disagree with the rule engine. A unit test fails if a content file contains a clinical value with a unit. The files use a tiny Markdown subset read by `lib/learn/parse.ts`; no Markdown library was added.
- **Learn URLs are topic slugs, not raw indicator ids** (`/learn/blood-pressure` covers `bp_systolic` + `bp_diastolic`). The mapping is `config/learn.ts`. Eleven topics: every indicator that has bands. Body weight, calories, stress and sleep quality have no bands in `config/thresholds.ts` and so no page of their own.
- **Learn pages are pre-rendered at build time** (`generateStaticParams`, unknown slug = 404); the browser never fetches Markdown.
- **"When to contact the flight surgeon" on risk cards is one sentence that defers to the engine's red/critical results**, not 17 hand-written medical statements (CLAUDE.md rule 6). "What the crew can do" stays inside the SPEC §2.1 list (exercise, sleep, nutrition, hydration, teamwork, reporting). All of it is our own wording; `content/riskGuidance.ts`.
- **`config/hazards.ts` created** (SPEC §2 says `content/hazards.ts`; CLAUDE.md §3 lists it under `config/`, which wins).
- **How the environment reaches the rule engine.** SPEC §4.4's environment bullet is descriptive emphasis and names no threshold change, so no threshold or status is changed per environment. The one concrete, spec-backed hook is CMB-SAM-01's "or first 3 days after gravity change", dropped in C1 because nothing recorded a gravity change. Now: changing environment between microgravity (spacecraft, station) and partial gravity (rover, moon base, mars base) stores `gravityChangedOn` on the astronaut; `buildMissionContext` turns it into `daysSinceGravityChange`; CMB-SAM-01 fires in the first 3 mission days **or** the first 3 days after that change. `RULES_VERSION` is now 1.1.0 and four vectors were added to `shared/rule-test-vectors.json` (the Python engine in C13 must pass them).
- **The yellow-softening window (7 days) also applies after a gravity change**, same four symptoms, yellow only. **Open item to confirm:** this is an extension of SPEC's "Mission day 1 to 7" by analogy. Note also that, as recorded in C1, no real rule currently produces a yellow caused solely by those four symptoms (CMB-SAM-01 is deliberately exempt), so softening has no visible effect today; the yellow-only invariant is enforced in code and tested for every environment with a synthetic flag.
- **The rover counts as partial gravity** and Moon <-> Mars base is not a gravity change (both "partial"). Simplest two-class model; a real Moon-to-Mars move passes through a spacecraft anyway.
- **`gravityChangedOn` is a new astronaut field** not in SPEC §6. C12 must add the column and C14 must sync it.

- **`DailyLog.firstReadings`** (a `Partial<Record<fieldId, number>>` on the same row) is how "store both readings" is implemented — SPEC §6.1/§6.2 give the `DailyLog` table one column per indicator, no second-reading column, so the original (pre-rest) value is kept in this side-map instead of inventing new top-level DB columns.
- **Saving a measurement form is a full replace of that date's measurement fields, not a merge.** If a field is blank on save (the astronaut cleared something they'd entered earlier that same day), it's cleared in Dexie too — "Save" means "this is what's true now," not "patch in whatever's non-empty." Re-opening a date still shows exactly what's saved for it (fetched live via `getLogForDate`), so nothing is silently lost from the astronaut's point of view either way.
- **The measurement-entry form uses plain `useState`, not React Hook Form** (unlike C2's `RegisterAstronautForm`). The per-field interactivity here — steppers, skip, live borderline detection, a secondary "second reading" input appearing conditionally, a date switch that reloads different saved data — doesn't fit RHF's submit-time-validation model well. Zod still validates (same schema, driving both the "impossible value" rejection and the borderline check's indicator lookup), just invoked directly via `safeParse` on save instead of through `useForm`.
- **State resets on `(astronautId, date)` change are done by adjusting state during render, not inside a `useEffect`.** `eslint-plugin-react-hooks`'s newer rule flags synchronous `setState` inside effects (cascading renders); React's own documented fix for "reset state when a key changes" is exactly this pattern (compare current vs. stored key during render, call `setState` conditionally). A real race was caught and fixed here too: `useLiveQuery` can keep returning the *previous* date's row for a render or two after the date changes (it resolves asynchronously), so the form only trusts a fetched row once its own `astronautId`+`date` fields actually match the current selection — not just "is it defined."
- **`/checkin` is enabled in the bottom nav now**, showing only the measurement-entry step (no wizard chrome, no symptoms/mood steps). C4 wraps this in the real stepper and this screen becomes one step inside it, rather than being rebuilt.

**2026-11-13 — C1 rule-engine ambiguity resolutions (SPEC §2.1/§3.2/§4.4)**

A batch of simplest-option choices made while implementing the rule engine, each kept deliberately narrow:

- **"A/B" statuses with no stated differentiator** (`CMB-HYP-01` "critical/red", `CMB-GLU-01` "red/critical", `CMB-DEHY-01`/`CMB-BACK-01`/`TRD-MOOD-01`/`TRD-WGT-01`/`TRD-RAD-01` "yellow/red"): always resolves to the **milder** of the two ranks (`lib/rules/status.ts` `milder()`). Reason: never invent extra severity the rule text doesn't unambiguously state; the milder tier is always at least what the rule guarantees.
- **Exercise and team_relations "red ... for 3+ days" bands** (SPEC §3.2): the per-day `Band` shape (`{status,min,max}`) has no day-count field, so the single-day band applies the numeric cutoff unconditionally (a single day of 20min exercise bands as "red" on its own), while `TRD-EXR-01`/`TRD-TEAM-01` separately implement the literal multi-day trend check (both land on "yellow" per §4.4's own wording, which is *lower* than §3.2's "red" label for the same 3-day pattern — a genuine spec self-contradiction we didn't try to paper over). In practice both can fire the same day; `overall` takes the worst of whichever is right, so nothing is lost. See `shared/rule-test-vectors.json` "TRD-EXR-01" and "TRD-TEAM-01" vectors, which deliberately show the red indicator + yellow trend coexisting.
- **`CMB-SAM-01` is not a target of the mission-phase softening modifier**, even though both its triggering symptoms (nausea_vomiting, dizziness) are in the §4.4 "soften yellow" list and it only ever fires within the softening window (missionDay ≤ 3 ⊂ ≤ 7). Tagging it would make the modifier silently cancel the rule out every time it fires. CMB-SAM-01 is already the dedicated, yellow-capped, early-mission rule for exactly this symptom pair, so the modifier's `causedBySymptoms` mechanism is left available for any *other* future rule instead (see `lib/rules/combos.ts` comment, and `lib/rules/modifiers.ts`'s own unit test since no current rule exercises that path through `evaluate()`).
- **Environment rule modifiers are a no-op in C1.** SPEC §4.4's environment bullet (rover/moon_base/mars_base/station/spacecraft) is descriptive emphasis for tip packs, not a concrete threshold change, and CLAUDE.md explicitly assigns "environment... rule modifiers wired into the engine" to C10. `applyModifiers()` already accepts `mission.environment` for a stable signature C10 can extend without touching C1's code.
- **"Excessive thirst" and "shaking/sweating"** (prose in `CMB-GLU-01`/`CMB-HYPO-01`) aren't in the formal §4.3 symptom enum, so only the enum-backed alternatives (`nausea_vomiting`, `abdominal_pain`, `dizziness`, `fatigue`) are implemented.
- **`CMB-SAM-01`'s "or first 3 days after gravity change"** clause is dropped — no gravity-change-event input exists anywhere in the spec's data model, so only the `missionDay <= 3` clause is implemented.
- **Radiation is modeled as "% of budget"**, not raw mSv, because SPEC §3.2's own bands are stated in budget-percent terms ("within budget" / ">80%" / ">100%"). `radiation_dose_pct` is a computed value (today's `radiation_msv` ÷ `mission.radiationDailyBudgetMsv` × 100); if no daily budget is configured the indicator is simply skipped (radiation is explicitly optional per §3.1).
- **Exercise is banded as one combined `exercise_minutes` value** (`exercise_resistance_min + exercise_cardio_min`), since §3.2's band row is a single "Exercise (min/day)" line even though §3.1 tracks resistance/cardio as two separate numbers.
- **BP has no single combined "blood_pressure" indicator entry.** `bp_systolic` and `bp_diastolic` are banded independently (their own rule ids `BP-SYS-01`/`BP-DIA-01`); "the worse of the two parts" (§3.2) falls out naturally from the engine's final overall-status reduction (worst-of-everything) and from combo rules that explicitly compute `worst(bp_systolic, bp_diastolic)` (e.g. `CMB-HYP-01`) — no separate synthetic indicator was needed.
- **Escalation level is a fixed mapping from `overall` status** (green→none, yellow→self_care, red→contact_surgeon, critical→emergency), not a per-rule-specified level. Reason: simplest deterministic rule, and it matches every individual rule's described escalation text when checked by hand.
- **A value that matches no configured band defaults to `"yellow"`**, not green, so an unexpected/out-of-table reading is never silently treated as fine. Currently unreachable in practice (sleep's upper yellow band and the two open-ended extremes of most tables cover every real input), but kept as a safety net — see `lib/rules/bands.ts` `matchBand()`.
- **`Hazard` type is defined locally in `config/thresholds.ts`**, not in a `config/hazards.ts` content file. SPEC §2 (not read this chunk) owns the full hazard content table and is C10's job; the 5 hazard ids used here (`radiation`, `isolation`, `distance`, `gravity`, `closed_environment`) come straight from §2.1's own "Main hazard(s)" column, which *was* in this chunk's reading list.
- **`source` field is a single shared generic string** for every indicator ("General adult clinical reference... see SPEC §3.2") rather than a fabricated specific citation (e.g. a named guideline), since SPEC itself doesn't name a specific source beyond "general adult clinical references" — inventing a more specific one would misrepresent provenance. `verified: false` on every entry per SPEC §3.3.
